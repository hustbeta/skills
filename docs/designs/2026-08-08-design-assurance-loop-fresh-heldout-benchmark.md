# Design Assurance Loop 全新跨域盲测设计

## 背景

iteration-1 已把 H2、H3 和 C1 固化为历史回归案例，并完成人工修订后的 Skill / no-Skill 对比。它们可以证明已知缺陷没有回归，但已经参与过裁决，不能继续承担通用性证明。

本轮使用两个全新合成案例验证通用机制。案例替换领域、实体和术语，不引用原项目名称、路由或符号；评测期间冻结当前 Skill 和 rubric，不依据中途结果调参。

## 目标

- 验证 reviewer 能否依据设计与代码证据识别重大安全缺陷，而不是依据部署猜测降低严重度。
- 验证 reviewer 能否发现共享实现的其它真实消费者，同时把范围取舍留给用户裁决。
- 验证 reviewer 能否区分单请求上限与并发累计成本，并在缺少影响证据时控制严重度。
- 验证 reviewer 能否把外部实现缺失记录为发布门禁，而不是制造 P0/P1。
- 对比加载当前 Skill 与不加载 Skill 的盲测结果，不修改当前 Skill。

## 非目标

- 不用 H2、H3、C1 的原始项目词汇或代码结构生成答案模板。
- 不修改 `design-assurance-loop/SKILL.md` 或 `references/review-rubric.md`。
- 不开发新的 benchmark harness、CI、grader 框架或通用权限组件。
- 不把两案的首次结果直接表述为 Skill 已具备普遍通用性。
- 不在 Gold 未经人工确认前注册正式 eval。

## 案例 A：跨租户导出下载

### 输入场景

某多租户报表服务提供交互式导出下载接口。已认证用户可以提交导出任务 ID；共享解析函数按全局任务 ID 读取记录并返回结果文件，但当前设计没有要求校验任务所属租户或创建者。附件证据能够串起用户可控 ID、全局查询和文件返回路径。

同一共享解析函数还被内部定时投递任务调用。交互式接口与定时任务的身份上下文不同，现有证据不足以决定两者必须采用同一种授权方式。

是否已部署、具体网络入口和外部可达性没有证据。

### Gold 边界

- 主要 finding 为 P0：设计允许已认证调用方通过选择其它租户的任务 ID 获取跨租户数据，直接破坏租户隔离这一核心安全不变量。
- P0 由输入中的设计与调用链证据成立；部署和网络可达性记为运行态 `unknown`，不降低设计 finding 的严重度。
- 必须引用共享解析函数的定时投递消费者，说明影响范围超过交互式入口。
- 定时投递入口的具体修改方式记为 `requires-user-decision`，不得因发现复用就自动扩大实施范围。
- 修订应要求可验证的租户或主体绑定，但不强制重写响应 JSON、建立全局权限框架或统一所有消费者的身份模型。

### Must-not-raise

- 不因缺少部署证据把已证明的设计安全缺陷降为 P1/P2。
- 不把“存在共享消费者”直接等同于“所有消费者必须同步修改”。
- 不要求与租户隔离无关的加密、审计平台、数据库迁移或全局鉴权重构。

## 案例 B：有界清单解析早于准入门禁

### 输入场景

某批处理服务接收外部客户端提交的 JSON 清单。处理器先读取并解析最多 8192 字节正文，随后才检查租户准入和应用层并发配额。单个请求的正文读取有明确上限，但多个并发连接可在进入配额判断前重复产生读取和解析成本。

附件没有提供可达到的并发量、worker / 连接模型、读取超时、内存或 CPU 退化数据。生产代理限制、外部执行器容量和目标测试结果也没有被验证。

需求已接受以下边界：既有集成密钥自动获得该清单类型的访问能力；不增加按类型授权或 migration；不记录业务正文；既有内部入口保持不变。

### Gold 边界

- 读取顺序 finding 为 P2：8192 字节只限制单请求成本，N 个并发连接仍可形成约 `N × 8192` 字节的累计读取与解析成本。
- 上游代理限制只影响风险规模和资源消耗位置，不改变应用层先读取后准入的事实。
- 缺少可达到并发量、资源耗尽或可复现服务降级证据，因此不得升级为 P0/P1。
- 生产代理、读取超时、worker 模型、外部执行器状态和目标测试结果记为 `unknown` 发布或验收门禁，而不是缺少证据的严重 finding。
- 已接受风险和非目标只进入残余风险，不重新扩入实施范围。
- 没有已接受 P0/P1 时，最终状态应为 `PASS`；P2 和 unknown 门禁保留在账本与残余风险中。

### Must-not-raise

- 不要求新增细粒度权限、migration、正文审计、内部入口迁移或通用 API 框架。
- 不把每个 unknown 分别升级为 P0/P1。
- 不以“可能被攻击”的抽象描述替代并发累计成本、发生条件和证据边界。

## 输入与 Gold 隔离

- executor 只接收当前设计、证据附件和真实用户式 blind prompt。
- executor 不得接收 catalog、`evals.json`、expectations、decision ledger 或本设计文档。
- case-specific Gold 使用具体合成符号以校验证据链；评分能力使用“租户绑定”“共享消费者”“并发累计成本”和“unknown 门禁”等通用机制。
- 先生成输入和 evaluator-only decision ledger，再由用户核对 Gold；用户确认前不加入正式 `evals.json`。

## 对比执行

每个案例运行两种配置，每种配置独立执行三次：

1. Treatment：加载当前 `design-assurance-loop` Skill 及其必需 reference。
2. Baseline：不加载该 Skill，只给出相同 blind prompt 和输入附件。

共执行 `2 案例 × 2 配置 × 3 次 = 12` 次。每次使用 fresh context；Treatment 与 Baseline 的输入除 Skill 外保持一致。原始输出、评分和人工裁决分别保存，禁止用后一次输出修补前一次结果。

临时运行产物放入已忽略的 `design-assurance-loop-workspace/iteration-2/`，不污染正式 Skill 输入。

## 评分与通过标准

### 案例 A

- 三次 Treatment 均识别跨租户读取为 P0，并引用用户可控 ID、无租户约束查询和文件返回证据。
- 三次 Treatment 均不因部署可达性 unknown 降低设计 P0。
- 三次 Treatment 均识别共享定时消费者，并把其具体处置记为 `requires-user-decision`。
- 不扩大 Must-not-raise 中的实施范围。

### 案例 B

- 三次 Treatment 均以 `N × 8192` 说明累计成本，并保持 P2。
- 三次 Treatment 均为零 false P0/P1。
- unknown 被记录为发布或验收门禁，accepted risk 与 non-goal 未被重新升级。
- 最终状态与剩余 finding 一致。

### 对比结论

- 报告两种配置逐项通过率、false P0/P1、证据准确性和边界遵守情况，不只报告总分。
- 如果两种配置都通过，不修改 Skill；结论仅为当前案例未显示增量收益。
- 如果 Treatment 通过而 Baseline 稳定失败，只记录当前两个新领域上的增量证据，不直接宣称全面通用。
- 同一通用能力在三次 Treatment 中至少两次失败，且人工复核确认 Gold 与输入充分时，才算稳定缺口。
- 使用本轮结果修改 Skill 时，两案立即转为 `historical-regression`；修改后的 Skill 必须再用新的未见案例验证，不能复用本轮成绩证明改进。

## 用户复核点

在创建附件和运行 benchmark 前，用户只需确认：

1. 案例 A 的 P0、运行态 unknown 和共享消费者裁决边界是否正确。
2. 案例 B 的 P2、并发累计解释、unknown 门禁和 accepted-risk 边界是否正确。
3. 两案是否已足够脱离原项目词汇，能够测试通用机制而非答案记忆。

确认后再编写实施计划；若任一 Gold 边界存在争议，先修订本设计，不运行评测。
